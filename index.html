Detailed model assumptions & limitations
  • HolodoriDB source: 3★–5★ card identity, rarity, attribute, character/group IDs, level stat progression, Bloom effects, Active/Passive/Special levels, and Outfit Skills are normalized from structured HolodoriDB master data. Stable card and character IDs—not name substrings—drive logic.
  • Automated search scope: v3.3 can search 5★ only or all imported 3★–5★ team cards. “Best outfit from any card” can use any imported Outfit Skill (or any owned Outfit Skill in an owned-roster search). Search pruning is heuristic rather than a formal proof of the global optimum; retained finalists use the full selected scoring model.
  • Level and Bloom: each card’s Performance/Technique/Sense are calculated from the imported per-level base value, stat-distribution permil values, and cumulative Bloom stat bonuses. Bloom also selects the appropriate Lv.1/Lv.2 Active, Passive, and Special rows.
  • Active probabilities: the probability is read from the selected Active skill level (currently the familiar 37% / 46% / 55% values where applicable). Bloom can change the probability on cards whose Active Lv.2 differs.
  • Active conditions: team-composition conditions such as “2 Pure” or “2 Gen 3” are evaluated exactly from structured attribute/group IDs. In specific-chart Perfect-FC mode, Combo thresholds are evaluated from the exact number of notes before each activation check; LIFE and judgement-state requirements are treated as satisfied under the Perfect-FC assumption. Generic mode retains the older satisfied-state approximation.
  • Active timing and overlap: a card first checks after one full interval; checks repeat every interval; each successful Active lasts its listed duration. Specific-chart mode uses millisecond chart time and exact Perfect-FC note-weight coverage; generic mode uses the v2 one-second approximation. Only the highest successful overlapping Active Score UP is credited; equal magnitudes resolve left-to-right.
  • Passive targeting: imported Passive targets may be self, top 2, or top 3 eligible cards. Non-self recipients are chosen by current card Base Total; ties resolve left-to-right. A Passive only activates when its imported requirement count is met.
  • Outfits: Outfit/Leader effects and their structured triggers are evaluated effect-by-effect. An external sixth card may supply the Outfit Skill but does not become a team member.
  • Special Score Support: each ordered card fires at one of the chart’s five Special trigger timestamps. Score Support sources add with one another, then multiply the currently effective Active Score UP. A Special therefore contributes only while an Active is actually effective; it is not modeled as standalone direct Score UP. Generic mode approximates this interaction with empirically fitted r51 average-chart slot exposures of 0.894 / 1.191 / 1.410 / 1.517 / 1.063 by position.
  • SAR: imported Skill Activation Rate effects multiplicatively boost Active probabilities during the Special window, capped at 100%. In specific-chart mode SAR changes only activation checks whose exact timestamps fall inside that Special window; Perfect-FC Combo/LIFE/Judgement assumptions are applied consistently. Generic mode retains duration/slot weighting.
  • Lower-rarity secondary effects: 3★/4★ Special effects such as LIFE recovery or judgement enhancement are imported but do not add score in the current model. Their Score Support component is still modeled when present.
  • Bloom 5 board effects: 4★/5★ Bloom 5 primarily upgrades Skill Tree Connect/Board effects, which remain outside this model. Accordingly, Bloom 4 and 5 can be identical here when no modeled stat/skill effect changes.
  • Score model: “Other score bonus” is added directly. The result is a comparative expected index, not the game’s literal displayed score. Specific-chart mode includes exact chart note density, DB-derived Perfect note coefficients, DB-derived combo weighting, real Special timestamps, and exact SAR/check alignment. Optimizer search excludes Holomem Board; Comparison can optionally apply only Board Active Skill activation frequency. Memory, Member Power-Up, Fever, other Board effects, and hidden/unknown mechanics remain outside the model.
  • Interpretation: rankings are expectations, not guarantees. Gaps below roughly 2% should be treated as single-run near-ties because normal Active proc variance can readily reverse them.
  • Roster identity: two cards sharing the same HolodoriDB characterId cannot coexist in the five-member team. This naturally handles normal/Summer variants without name hacks.

Changelog Current version: v3.5.0

Release history and model/UI changes.

v3.5.0 — 2 August 2026

  • Corrected Score Support semantics: Special Skills that grant Score Support no longer add standalone direct score. Passive, Outfit, and concurrent Special Score Support add together and multiply the currently effective Active Score UP, matching observed in-game HUD behavior.
  • Exact chart interaction: Special support now follows the real Special window and only contributes where an Active is actually effective; SAR still modifies only activation checks inside its real window, and its additional Special-support value is attributed to SAR uplift.
  • Generic recalibration: refit the average-chart slot exposures against the corrected 702-chart model to 0.894 / 1.191 / 1.410 / 1.517 / 1.063. The 30-team × 702-chart validation set has ~2.9% mean absolute deviation; a held-out 10-team subset was ~2.86%.
  • Updated search heuristics so Special value is treated as support-on-Active rather than direct score, and ensured Score Support Outfit candidates remain represented during bounded Outfit screening.

v3.4.3 — 1 August 2026

  • Filter-first selectors: replaced editable combobox-style card/song search with a separate selected-value control plus a dedicated text filter and matching result list.
  • Partial substring filtering now behaves consistently with Owned, Require, and Exclude lists: typing filters candidates without overwriting the current selection until a result is clicked.
  • Applied to build-around cards, fixed Outfit selection, Optimizer/Comparison song selection, all Comparison team positions, and Comparison Outfit selection. Scoring/search mathematics are unchanged from v3.4.1.

v3.4.1 — 1 August 2026

  • Comparison Board Active frequency: each of the ten comparison slots can optionally apply +4%, +8%, or +12% Active Skill activation frequency. Effective interval is modeled as base interval ÷ (1 + frequency bonus), matching the observed 35 s → 31.25 s behavior at +12%.
  • Copy A → B: Team B can copy Team A's cards, Level, Bloom, Board Active settings, and Outfit Skill in one click for one-change comparisons.
  • Optimizer search remains Board-neutral; this experimentally validated Board timing control is intentionally limited to Comparison for now.

v3.4.0 — 1 August 2026

  • Searchable selectors: every direct card and song picker now supports text search while preserving the underlying native selection state.
  • Persistent search engine: Optimizer and Comparison reuse an initialized Web Worker when the effective card roster/progression is unchanged, retaining precomputed card maps, Outfit signatures, and typed scratch buffers across runs.
  • Maintainable source layout: v3.4 adds a deterministic developer source distribution separating HTML/CSS/application code from the scoring/search worker, plus independent app/model/card-schema/chart-schema version metadata. The source archive is optional and separate from the player package.
  • The scoring/search worker source is unchanged from v3.3.1.

Model v3.5 scoring documentation

Scoring equations, data pipeline, assumptions, and search behavior.

This section describes the optimizer model, not the game’s proprietary internal formula. All calculations use unrounded values internally; the results table rounds only for display.

Important: the optimizer still reports a comparative expected index rather than the game’s literal displayed score. Specific-chart mode uses the bundled validated r51 note timing, Perfect-FC note/combo weights, chart Special timestamps, and SAR/check alignment. Optimizer search remains Board-neutral; Comparison can optionally model only Board Active Skill activation frequency. Memory, Member Power-Up, Fever, other Board effects, hidden rounding, and other unknown systems remain omitted.
Validation status: release QC establishes data integrity, scorer consistency, and search correctness on tested spaces. The Generic-vs-Specific-Chart deviation figures below are internal model comparisons, not measurements against observed in-game scores. Empirical gameplay validation is still required to establish how closely the model matches the live game.
1. Hybrid architecture, version boundaries, card data, chart data, and artwork

v3.2 keeps development-time data work separate from the user-facing runtime. The Python toolchain joins and validates HolodoriDB card/master tables, compiles song+difficulty metadata, and compiles validated raw SUS charts into a normalized release companion or accepts an already-normalized provider snapshot. The browser receives normalized card data plus a compact lazy-loaded chart companion; it does not need Python and does not download/decrypt game chart resources.

HolodoriDB master tables + optional validated chart source → Python normalizer/compiler → card snapshot + chart snapshot → standalone HTML/JavaScript optimizer

The chart-provider boundary is intentionally replaceable. A future HolodoriDB-provided timing feed can generate the same Holodori_Chart_Timelines.json schema without changing the browser scoring engine. v3.2 ships 702 validated non-tutorial live r51 timelines across the 708 metadata rows. Rebellion Normal and save our hearts Easy are absent from the live r51 resource catalog; the four m9999 tutorial charts are intentionally unsupported. If the companion file is missing, the app falls back safely to metadata + generic scoring.

The Python reference model independently materializes progression and evaluates ordered teams. Release QC compares it against the production JavaScript worker for generic and chart-aware scoring.

Version boundaries: app/UI version, scoring-model version, normalized card-data schema, chart-pack schema, HolodoriDB source hash, and live chart revision are tracked independently. A new chart pack therefore does not imply changed scoring equations, and a UI release does not silently change the mathematical model.

Development layout: v3.4 provides a rebuildable developer source distribution separating document structure/CSS/application code from the scoring-search worker. It is distributed separately so the player package remains lean; the runtime stays the same simple local HTML + chart companion.

Card assetId is used only by the presentation layer to resolve remote HolodoriDB WebP artwork; image availability never affects scoring.

Runtime remains offline-capable: no game-CDN downloader, decryptor, Python runtime, or raw SUS file is required. The extracted release folder contains the HTML plus a normalized chart-data companion loaded locally.
2. Level and Bloom stat calculation

For a selected card level ℓ, HolodoriDB supplies a per-level parameterBaseValue V(ℓ) and card-specific Performance/Technique/Sense permil weights wP, wT, wS. Bloom stages may add a cumulative All-Stats fraction b.

P = ceil[V(ℓ) × wP/1000 × (1+b)]    T = ceil[V(ℓ) × wT/1000 × (1+b)]    S = ceil[V(ℓ) × wS/1000 × (1+b)]

The imported per-level data gives absolute maximum levels of 60 / 70 / 80 for 3★ / 4★ / 5★ in the current snapshot. Bloom also selects the appropriate Active, Passive, and Special skill level. For 4★/5★, Bloom 5 currently upgrades Skill Tree Connect/Board effects rather than a modeled scoring effect, so Bloom 4 and Bloom 5 may be identical in this optimizer.

3. Structured eligibility, conditions and Passive Top-N targeting

Attribute and generation/group requirements use stable IDs. A Gen 3 requirement therefore checks membership in grp-gen_3; ID Gen 3 is a different group ID and cannot match accidentally. Two cards with the same characterId cannot coexist.

N(c) = ∑i=15 𝟙{card i satisfies structured condition c}

For a non-self Passive with imported target count k, the skill activates only when at least k eligible cards exist. Recipients are the k eligible cards with highest current Base Total P+T+S; ties resolve left-to-right.

TopN(c,k) = first k cards after sorting eligible cards by (−Base Total, position)

Self-target Passives have an activation clause encoded only in the official generated description in this master snapshot. The normalization step parses that clause once, resolves the exact attribute/group to a stable ID, and rejects the data update if it cannot be resolved.

4. Active Skills, Perfect-FC chart timing, and overlap

Each materialized card uses the Active Lv.1/Lv.2 row selected by Bloom. A card first checks after one full interval and then every interval. In specific-chart mode those checks are placed on the real chart timeline in milliseconds. Combo-threshold magnitudes are selected from the number of Perfect-FC notes strictly before the check; LIFE/Judgement requirements are treated as satisfied for the current Perfect-FC model.

Comparison-only Board timing: the optional +4/+8/+12% Holomem Board Active Skill activation-frequency setting uses effective interval = base interval / (1 + bonus). This interpretation is supported by an observed 35 s Active producing an approximately 31.25 s check grid at +12%. Because this shifts the entire check grid, a particular chart can gain or lose modeled score depending on note/SAR alignment even though the average-chart effect is generally favorable.

Each successful Active covers [check, check + duration). The scorer measures the actual Perfect-FC chart weight inside every overlap segment rather than averaging by elapsed seconds.

E[winning Active] = ∑ chart-weight segment × ∑i magnitudei · pi · ∏j higher than i(1−pj)

Only the highest successful overlapping Score UP is credited. Equal magnitudes resolve left-to-right. Generic mode retains the older one-second duration approximation for compatibility.

5. Team stat and Score Support

Passive stat effects are additive against each recipient’s materialized card stats. Triggered Outfit stat effects are added from the team’s materialized base-stat sums. Passive and Outfit Score Support multiply only the winning Active magnitude.

Team Stat = Passive-adjusted card stats + triggered Outfit stat additions
Adjusted Active = expected winning Active after Passive Support + Outfit Support + Special Support + modeled SAR uplift
6. Outfit/Leader Skills

Every imported card has a Leader/Outfit record. Its one or two effects are evaluated independently using structured triggers; all current Leader effects target the whole team. “Best outfit from selected five” tests only team cards. The current “best outfit from any card” auto-search tests 5★ Outfit Skills only. A manually selected specific Outfit may come from any rarity, and Team Comparison allows any-rarity Outfit selection.

7. Special Score Support and SAR

Specific-chart mode uses the chart’s five actual Special trigger timestamps. The observed in-game behavior is modeled as additive Score Support: Passive, Outfit, and any concurrent Special Score Support percentages add together, and that total multiplies the currently effective Active Score UP. A Special Score Support effect therefore has no standalone score value when no Active is effective.

Supported Active = Active Score UP × [1 + Passive Support + Outfit Support + ∑ active Special Support]

For Special i, the exact chart contribution is the additional expected winning-Active value inside its real window:

Special Support uplifti = ∑segments in Special i chartWeightShare × E[winning Active raw] × SpecialSupporti

Concurrent Special Score Support effects add before multiplying the Active. For an imported SAR effect q, Active probability is capped at 100%:

pi,SAR = min[1, pi(1+q)]

In chart mode the probability boost applies only to Active checks whose timestamps actually fall inside the relevant Special window; a boosted proc then uses the card’s ordinary Active duration. Any extra Special-support value caused by those additional SAR-driven procs is counted inside SAR uplift rather than double-counted as baseline Special support. Fever is deliberately ignored because the model targets single-player Perfect-FC optimization.

8. Chart-adjusted Expected Index
Expected Index = Team Stat × (1 + total modeled expected score bonus / 100)

In specific-chart mode, the score-bonus term is weighted by actual Perfect-FC note timing/weight and real Special timing. It is still a comparative expected index, not a reconstruction of the game’s literal displayed score. Generic mode reports a chart-agnostic Stat × Score approximation.

After correcting Special Skills to behave as Score Support on Active Skills rather than standalone direct score, Generic mode was recalibrated from scratch against the 702 validated non-tutorial r51 timelines. The fitted average-chart position exposures are 0.894 / 1.191 / 1.410 / 1.517 / 1.063 for positions 1–5.

10. v3.3 scalable search strategy

v3.2 retains the bounded beam + structured synergy/diversity rescue + local one-card-swap architecture introduced in v2.1. It does not enumerate the full five-card space. Cheap screening keeps a bounded frontier; stronger complete candidates are then rescored with the selected generic or chart-aware model.

partial team → projected completion → quick structured screen → beam + feature rescue → local polish → exact chart/generic refinement → finalist order verification

Specific-chart quick screening is intentionally approximate so search remains tractable: exact overlap, SAR alignment, Outfit effects, and real chart timing are applied to retained refinement/finalist evaluations. Only the strongest finalists receive exhaustive 5! = 120 order verification.

Fast, Balanced and Thorough increase beam width, rescue quota, extension breadth, polish seeds, and exact-order finalist count.

Optimality caveat: this remains a best-found heuristic search, not a formal proof of the global optimum. Candidate pruning can theoretically discard the true optimum. QC therefore includes an exhaustive small-pool chart search where the production search must reproduce the exact Top 10.
11. Team comparison and proc-variance simulation

Team Comparison uses the same two scoring timelines as Optimizer. Specific Chart evaluates both fixed ordered teams on the selected exact Perfect-FC timeline, including chart-weighted Active overlap, real Special triggers, combo state, and SAR-adjusted activation checks. Generic uses the calibrated average-chart model.

The expected percentage difference for A relative to B is:

Difference(A vs B) = [IndexA/IndexB − 1] × 100%

The comparison simulation randomizes Active procs to estimate how often one n-run average beats the other. In Specific Chart mode, those proc checks occur at their real chart timestamps and SAR changes the probability only for checks inside the exact SAR window.

Interpretation: the displayed win chance is model-based, not a p-value or observed gameplay result.
12. What v3.5.0 deliberately does not calculate
  • Holomem Board bonuses are not used by Optimizer search. Comparison can optionally model the experimentally supported +4/+8/+12% Active Skill activation-frequency nodes per member; other Board bonuses, Memory Bonuses, Member Power-Up Bonuses, and Skill Tree Connect/Board score effects remain outside the model.
  • Fever/multiplayer mechanics.
  • Non-Perfect-FC player accuracy, misses, or a custom judgement distribution.
  • Literal in-game displayed score, difficulty/base-score constants, hidden rounding, or account-level systems not represented in the imported card model.
  • Direct score value from LIFE recovery or judgement-enhancement secondary effects on lower-rarity cards.
  • Specific-chart scoring for rows with no validated five-trigger timeline. In bundled r51 data, Rebellion Normal and save our hearts Easy are missing live resources, while the four m9999 tutorial rows use only two triggers; select another supported difficulty or import a newer validated snapshot.
  • Undocumented mechanics, future schema changes, or unsupported effect types. Validation is designed to fail closed rather than silently replace known-good data.
