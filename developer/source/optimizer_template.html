Detailed model assumptions & limitations
  • HolodoriDB source: 3★–5★ card identity, rarity, attribute, character/group IDs, level stat progression, Bloom effects, Active/Passive/Special levels, and Outfit Skills are normalized from structured HolodoriDB master data. Stable card and character IDs—not name substrings—drive logic.
  • Automated search scope: v2.2 can search 5★ only or all imported 3★–5★ team cards. “Best outfit from any card” can use any imported Outfit Skill (or any owned Outfit Skill in an owned-roster search). Search pruning is heuristic rather than a formal proof of the global optimum; retained finalists use the full score model.
  • Level and Bloom: each card’s Performance/Technique/Sense are calculated from the imported per-level base value, stat-distribution permil values, and cumulative Bloom stat bonuses. Bloom also selects the appropriate Lv.1/Lv.2 Active, Passive, and Special rows.
  • Active probabilities: the probability is read from the selected Active skill level (currently the familiar 37% / 46% / 55% values where applicable). Bloom can change the probability on cards whose Active Lv.2 differs.
  • Active conditions: team-composition conditions such as “2 Pure” or “2 Gen 3” are evaluated exactly from structured attribute/group IDs. Combo, LIFE, and judgement-state conditions are assumed satisfied because exact chart/gameplay state is not modeled.
  • Active timing and overlap: a card first checks after one full interval; checks repeat every interval; each successful Active lasts its listed duration. Timing uses a one-second grid. Only the highest successful Active Score UP is credited at a time; equal magnitudes resolve left-to-right.
  • Passive targeting: imported Passive targets may be self, top 2, or top 3 eligible cards. Non-self recipients are chosen by current card Base Total; ties resolve left-to-right. A Passive only activates when its imported requirement count is met.
  • Outfits: Outfit/Leader effects and their structured triggers are evaluated effect-by-effect. An external sixth card may supply the Outfit Skill but does not become a team member.
  • Ordinary Specials: direct Score UP is normalized as magnitude × duration ÷ song length. Combo-biased mode uses slot weights 0.92 / 0.96 / 1.00 / 1.04 / 1.08 as a proxy for increasing combo value; exact chart note density is unavailable.
  • SAR: imported Skill Activation Rate effects multiplicatively boost the selected Active probabilities during the modeled Special window, capped at 100%. Structured team-composition SAR triggers are evaluated; Combo/LIFE triggers are assumed satisfied. Exact timestamps and Active-check alignment are still approximated by duration/slot weighting.
  • Lower-rarity secondary effects: 3★/4★ Special effects such as LIFE recovery or judgement enhancement are imported but do not add score in the current model. Their direct score component is still modeled.
  • Bloom 5 board effects: 4★/5★ Bloom 5 primarily upgrades Skill Tree Connect/Board effects, which remain outside this model. Accordingly, Bloom 4 and 5 can be identical here when no modeled stat/skill effect changes.
  • Score model: “Other score bonus” is added directly. Stat × Score is a comparative index, not the game’s literal Unit Score; Holomem Board, Memory, Member Power-Up, exact note density/combo scoring, and hidden mechanics are omitted.
  • Interpretation: rankings are expectations, not guarantees. Gaps below roughly 2% should be treated as single-run near-ties because normal Active proc variance can readily reverse them.
  • Roster identity: two cards sharing the same HolodoriDB characterId cannot coexist in the five-member team. This naturally handles normal/Summer variants without name hacks.

Methodology, data pipeline and mathematical definitions v2.2 model documentation

This section describes the optimizer model, not the game’s proprietary internal formula. All calculations use unrounded values internally; the results table rounds only for display.

Important: Stat × Score remains a comparative index. It is not the literal in-game Unit Score because Holomem Board, Memory, Member Power-Up, exact per-note/combo scoring, hidden rounding, and some non-scoring skill effects are omitted.
1. v2.2 hybrid architecture and HolodoriDB normalization

v2.2 separates development-time data work from the user-facing runtime. The canonical release snapshot is produced by the included Python toolchain: raw HolodoriDB tables are joined, normalized, validated, packed, hashed, and injected into the standalone HTML. The browser still contains a compatibility normalizer so the existing optional live-update button can validate newer HolodoriDB data without requiring Python on the user's machine.

HolodoriDB raw tables → Python normalizer/validator → packed release snapshot → standalone HTML/JavaScript optimizer

The Python reference model independently materializes card progression and evaluates ordered five-card teams. Release QC compares it against the JavaScript worker to detect cross-language drift in stats, Passives, Active overlap, Specials, SAR, Outfit effects, and the final Expected Index.

Schema v2 additionally preserves each card's raw assetId. It is not used by scoring, but provides a stable future hook for card artwork.

Runtime remains standalone: Python is not required to open or use the released HTML. It is the build/update/reference layer for maintaining the project.
2. Level and Bloom stat calculation

For a selected card level ℓ, HolodoriDB supplies a per-level parameterBaseValue V(ℓ) and card-specific Performance/Technique/Sense permil weights wP, wT, wS. Bloom stages may add a cumulative All-Stats fraction b.

P = ceil[V(ℓ) × wP/1000 × (1+b)]    T = ceil[V(ℓ) × wT/1000 × (1+b)]    S = ceil[V(ℓ) × wS/1000 × (1+b)]

The imported per-level data gives absolute maximum levels of 60 / 70 / 80 for 3★ / 4★ / 5★ in the current snapshot. Bloom also selects the appropriate Active, Passive, and Special skill level. For 4★/5★, Bloom 5 currently upgrades Skill Tree Connect/Board effects rather than a modeled scoring effect, so Bloom 4 and Bloom 5 may be identical in this optimizer.

3. Structured eligibility, conditions and Passive Top-N targeting

Attribute and generation/group requirements use stable IDs. A Gen 3 requirement therefore checks membership in grp-gen_3; ID Gen 3 is a different group ID and cannot match accidentally. Two cards with the same characterId cannot coexist.

N(c) = ∑i=15 𝟙{card i satisfies structured condition c}

For a non-self Passive with imported target count k, the skill activates only when at least k eligible cards exist. Recipients are the k eligible cards with highest current Base Total P+T+S; ties resolve left-to-right.

TopN(c,k) = first k cards after sorting eligible cards by (−Base Total, position)

Self-target Passives have an activation clause encoded only in the official generated description in this master snapshot. The normalization step parses that clause once, resolves the exact attribute/group to a stable ID, and rejects the data update if it cannot be resolved.

4. Active Skills, Bloom-dependent probability and overlap

Each materialized card uses the Active Lv.1/Lv.2 row selected by Bloom. The worker reads its exact activation probability, interval and duration. Team-composition conditional magnitudes are evaluated from structured triggers; Combo/LIFE/Judgement gameplay-state conditions are assumed satisfied.

ai(t) = 𝟙{t ≥ Ii and (t mod Ii) < di}

Only the highest successful Active Score UP is credited at a time. Equal magnitudes resolve left-to-right. If Hi is the set of higher-priority overlapping cards, the expected probability that card i is the credited winner at second t is:

wi(t) = ai(t)pi ∏j∈Hi[1 − aj(t)pj]
5. Team stat and Score Support

Passive stat effects are additive against each recipient’s materialized card stats. Triggered Outfit stat effects are added from the team’s materialized base-stat sums. Passive and Outfit Score Support multiply only the winning Active magnitude.

Team Stat = Passive-adjusted card stats + triggered Outfit stat additions
Adjusted Active = expected winning Active after Passive Support + Outfit Support + modeled SAR uplift
6. Outfit/Leader Skills

Every imported card has a Leader/Outfit record. Its one or two effects are evaluated independently using structured triggers; all current Leader effects target the whole team. “Best outfit from selected five” tests only team cards. The current “best outfit from any card” auto-search tests 5★ Outfit Skills only. A manually selected specific Outfit may come from any rarity, and Team Comparison allows any-rarity Outfit selection.

7. Ordinary Specials and SAR

Direct Special Score UP is normalized by duration and song length. Combo-biased mode multiplies the five left-to-right Special slots by 0.92 / 0.96 / 1.00 / 1.04 / 1.08.

Direct Special bonus = magnitude × duration / song length × slot weight

For an imported SAR effect q, the temporary Active probability is capped at 100%:

pi,SAR = min[1, pi(1+q)]

The model compares expected Active output at normal versus boosted probabilities and scales the uplift by SAR duration and Special position. Exact Special timestamps, chart note density, and Active-check alignment are not yet available.

8. Stat × Score index
Stat × Score = Team Stat × (1 + Total modeled score bonus / 100)

Total modeled score bonus combines adjusted Active output, direct Special contribution, and the user-entered Other score bonus. It does not include omitted account systems or exact chart scoring.

9. v2.2 scalable search strategy

The v2.2 runtime preserves v2.1's scalable search: it does not enumerate every five-card composition. It builds teams incrementally and keeps a bounded frontier of promising partial teams. A global score beam is supplemented by structured attribute/group feature lanes so temporarily weaker partial teams can survive long enough to complete a synergy.

partial team → greedy projected completion → quick structured score → global beam + feature rescue → five-card finalists

From depth three onward, each partial team explores a bounded extension set: high-static-value cards, cards matching structured features already present or requested by its skills, and deterministic spread samples from the remainder of the pool. This prevents runtime from scaling directly with the entire roster size.

Five-card candidates then receive local one-card-swap polishing. The strongest candidates are rescored with the full overlap/SAR model under representative orders. Only the strongest final compositions receive exhaustive 5! = 120 order verification.

Approximate work ≈ O(team depth × beam width × bounded extension budget), rather than O(N⁵)

Fast, Balanced and Thorough increase beam width, feature-rescue quota, extension breadth, local-polish seeds, and exact-order finalist count.

Optimality caveat: v2.2 is a scalable best-found search, not a mathematical branch-and-bound proof. Candidate pruning can theoretically discard the global optimum. Higher effort modes reduce that risk at higher runtime; retained finalists are still scored exactly under the documented model.
10. Team comparison and proc-variance simulation

Team Comparison can use 3★–5★ cards with independent level/Bloom values. The expected percentage difference for A relative to B is:

Difference(A vs B) = [IndexA/IndexB − 1] × 100%

The comparison then simulates individual baseline Active procs. For a selected set size n, it estimates how often the n-run average of Team A beats the n-run average of Team B. Direct Specials and the current SAR approximation remain deterministic because their exact chart timing is unavailable.

Interpretation: the displayed win chance is a model-based probability, not a p-value and not evidence from observed gameplay.
11. What the model deliberately does not calculate
  • Holomem Board Bonuses, Memory Bonuses, Member Power-Up Bonuses, or Skill Tree Connect/Board score effects.
  • Exact per-note density, exact combo multipliers, chart-specific Special timestamps, or difficulty-specific scoring curves.
  • Exact SAR-to-Active-check alignment; SAR remains duration- and position-weighted.
  • Failure of Combo/LIFE/Judgement gameplay-state conditions; those are assumed satisfied. Team-composition conditions are now evaluated exactly.
  • Direct score value from LIFE recovery or judgement-enhancement secondary effects on lower-rarity cards.
  • Undocumented mechanics, hidden precision, future schema changes, or future effect types not yet supported. Online updates are validated so incompatible data does not silently replace the last-known-good snapshot.
